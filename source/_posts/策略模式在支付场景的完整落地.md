## 背景

写一个支付接口，最直觉的写法是这样：

```java
public BigDecimal pay(String type, BigDecimal amount) {
    if ("ALIPAY".equals(type)) {
        // 阿里支付逻辑
        return doAlipay(amount);
    } else if ("WECHAT".equals(type)) {
        // 微信支付逻辑
        return doWechatPay(amount);
    } else if ("UNION".equals(type)) {
        // 银联支付逻辑
        return doUnionPay(amount);
    }
    throw new IllegalArgumentException("不支持的支付方式: " + type);
}
```

能跑。但只要需求一变就难受：

- 加一种支付方式 → 改这个方法，加一个 `else if`
- 改某个渠道的费率 → 改这个方法，可能影响其他分支
- 想给某个渠道单独加日志/重试 → 继续往里塞代码

问题不在于 `if-else` 本身，而在于**这段代码同时违反了两个原则**：

1. **单一职责原则**：一个方法承担了所有支付渠道的逻辑
2. **开闭原则**：新增渠道必须修改已有代码，而不是扩展

策略模式就是为了解决这个。

## 策略模式是什么

> 定义一系列算法，把它们一个个封装起来，并且使它们可以相互替换。策略模式让算法独立于使用它的客户端而变化。

三个角色：

| 角色 | 职责 | 支付场景中的对应 |
| --- | --- | --- |
| **Strategy（策略接口）** | 定义算法的公共接口 | `PayStrategy` |
| **ConcreteStrategy（具体策略）** | 实现具体算法 | `AliPayStrategy`、`WechatPayStrategy` |
| **Context（上下文）** | 持有策略引用，对客户端暴露统一入口 | `PayContext` / `PayService` |

结构图：

```
        ┌─────────────┐
        │   Context   │────────────▶ ┌──────────────────┐
        │  PayService │  strategy    │  <<interface>>   │
        └─────────────┘              │   PayStrategy    │
                                     ├──────────────────┤
                                     │ + pay(amount)    │
                                     └──────────────────┘
                                              △
                     ┌────────────────────────┼────────────────────────┐
              ┌──────┴──────┐          ┌──────┴──────┐          ┌──────┴──────┐
              │ AliPay      │          │ WechatPay   │          │ UnionPay    │
              │ Strategy    │          │ Strategy    │          │ Strategy    │
              └─────────────┘          └─────────────┘          └─────────────┘
```

## 第一步：定义策略接口

```java
public interface PayStrategy {

    /**
     * 当前策略支持的支付方式
     */
    String getType();

    /**
     * 执行支付
     * @param amount 金额
     * @return 实际扣款金额（含手续费）
     */
    PayResult pay(BigDecimal amount);
}
```

返回值封装成一个对象，别直接返回 `BigDecimal` —— 后面要加交易号、渠道信息时会很痛苦：

```java
@Data
@AllArgsConstructor
public class PayResult {
    private boolean success;
    private BigDecimal actualAmount;  // 实付
    private BigDecimal fee;           // 手续费
    private String tradeNo;           // 渠道交易号
    private String message;

    public static PayResult fail(String message) {
        return new PayResult(false, BigDecimal.ZERO, BigDecimal.ZERO, null, message);
    }
}
```

## 第二步：实现具体策略

```java
@Component
public class AliPayStrategy implements PayStrategy {

    private static final BigDecimal FEE_RATE = new BigDecimal("0.006"); // 0.6%

    @Override
    public String getType() {
        return "ALIPAY";
    }

    @Override
    public PayResult pay(BigDecimal amount) {
        BigDecimal fee = amount.multiply(FEE_RATE)
                               .setScale(2, RoundingMode.HALF_UP);
        // 真实场景这里调用支付宝 SDK
        String tradeNo = "ALI" + System.currentTimeMillis();
        return new PayResult(true, amount.add(fee), fee, tradeNo, "支付宝支付成功");
    }
}
```

```java
@Component
public class WechatPayStrategy implements PayStrategy {

    private static final BigDecimal FEE_RATE = new BigDecimal("0.006");

    @Override
    public String getType() {
        return "WECHAT";
    }

    @Override
    public PayResult pay(BigDecimal amount) {
        BigDecimal fee = amount.multiply(FEE_RATE)
                               .setScale(2, RoundingMode.HALF_UP);
        String tradeNo = "WX" + System.currentTimeMillis();
        return new PayResult(true, amount.add(fee), fee, tradeNo, "微信支付成功");
    }
}
```

**关键点**：每个策略类只关心自己的逻辑，新增渠道 = 新增一个类，不动任何已有代码。

## 第三步：上下文 + Spring 自动装配

这是整个模式落地最实用的一步 —— **不要手写 Map 注册，让 Spring 容器帮你做**。

```java
@Service
public class PayService {

    private final Map<String, PayStrategy> strategyMap = new ConcurrentHashMap<>();

    /**
     * Spring 会注入所有 PayStrategy 的实现类
     * key = bean 名称，value = 策略实例
     */
    public PayService(List<PayStrategy> strategies) {
        for (PayStrategy strategy : strategies) {
            strategyMap.put(strategy.getType(), strategy);
            log.info("注册支付策略: {} -> {}",
                     strategy.getType(), strategy.getClass().getSimpleName());
        }
    }

    public PayResult pay(String type, BigDecimal amount) {
        if (amount == null || amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("支付金额必须大于 0");
        }

        PayStrategy strategy = strategyMap.get(type);
        if (strategy == null) {
            return PayResult.fail("不支持的支付方式: " + type);
        }
        return strategy.pay(amount);
    }
}
```

这里用了 Spring 的一个很实用的特性：**注入 `List<PayStrategy>` 会自动拿到容器中所有该接口的实现类**。

带来的好处：

```java
@Component  // 加上这一行，新渠道自动生效
public class UnionPayStrategy implements PayStrategy {
    @Override
    public String getType() { return "UNION"; }

    @Override
    public PayResult pay(BigDecimal amount) {
        // 银联逻辑
    }
}
```

**加一个支付方式，只写一个类，加一个 `@Component`。`PayService` 一行都不用改。** 这就是开闭原则。

## 第四步：Controller

```java
@RestController
@RequestMapping("/api/pay")
@RequiredArgsConstructor
public class PayController {

    private final PayService payService;

    @PostMapping
    public PayResult pay(@RequestParam String type,
                         @RequestParam BigDecimal amount) {
        return payService.pay(type, amount);
    }
}
```

## 改造前后对比

| 维度 | if-else 版本 | 策略模式版本 |
| --- | --- | --- |
| 新增渠道 | 修改已有方法 | 新增一个类 |
| 单个渠道的单元测试 | 难，要穿透所有分支 | 简单，直接测策略类 |
| 方法行数 | 随渠道数线性增长 | 恒定 |
| 改 A 渠道影响 B 渠道 | 有可能 | 不会 |
| 类数量 | 1 | 1 + N |

**代价是类变多了。** 这是策略模式唯一的显著成本，对于 3 个以上的分支通常是划算的。

## 进阶：用枚举消除魔法字符串

`"ALIPAY"` 这种字符串散落在代码里容易拼错。可以定义一个枚举：

```java
@Getter
@AllArgsConstructor
public enum PayType {

    ALIPAY("ALIPAY", "支付宝"),
    WECHAT("WECHAT", "微信支付"),
    UNION("UNION", "银联");

    private final String code;
    private final String desc;
}
```

策略接口改用枚举：

```java
PayType getType();
```

这样编译期就能发现拼写错误，IDE 也能自动补全。

## 适用场景与反模式

**适合用策略模式的信号：**

- 有一段逻辑里有 `if-else` 或 `switch` 分支数 ≥ 3，且**每个分支都是一整块完整算法**
- 这些分支**未来大概率会增加**
- 需要**在运行时动态切换**算法
- 想让算法能**被单独测试**

**不适合（反模式）：**

1. **只有 2 个分支且几乎不会变** —— 引入 3 个类换来一点点灵活性，得不偿失
2. **每个分支只有一两行代码** —— 用 `Map<String, Function>` 或者枚举就够了，别上纲上线
3. **策略之间需要共享大量状态** —— 说明它们不是独立的算法，该考虑模板方法模式
4. **把 Spring Bean 当纯策略用还手动 new** —— 那就享受不到依赖注入，策略里没法注入 Mapper、RedisTemplate

第 4 点是初学者最常见的坑：**策略类必须交给 Spring 管理（`@Component`），不能用 `new` 手动创建**，否则策略内部无法注入其他 Bean。

## 面试常问点

**Q：策略模式和工厂模式的区别？**

工厂模式关注**对象的创建**（怎么造出来），策略模式关注**算法的选择和替换**（怎么用）。实际项目里两者经常一起用：工厂负责创建策略对象，策略负责执行算法。上面的 `PayService` 构造函数里那张 Map 就带有一点简单工厂的味道。

**Q：策略模式和模板方法模式的区别？**

策略模式用**组合**（Context 持有 Strategy 引用），算法可以运行时替换；模板方法用**继承**（子类覆写父类抽象方法），算法骨架在编译期就固定了。策略更灵活，模板方法更适合"流程固定、只有某几步不同"的场景。

**Q：策略模式在 JDK / Spring 里的应用？**

- `Comparator<T>` 是最经典的策略接口，`Collections.sort(list, comparator)` 就是传入策略
- Spring 的 `Resource` 接口（`ClassPathResource` / `FileSystemResource` / `UrlResource`）
- Spring MVC 的 `HandlerMapping`、`ViewResolver`
- MyBatis 的 `Executor`（`SimpleExecutor` / `ReuseExecutor` / `BatchExecutor`）

## 小结

策略模式的核心价值不是"消除 if-else"（那只是副作用），而是**把变化的算法隔离到独立的类中，让新增变化不需要修改已有代码**。

判断要不要用的标准很简单：

> 这段分支逻辑，未来半年内还会加新的分支吗？
>
> 会 → 上策略模式。不会 → 老实写 if-else，别过度设计。
